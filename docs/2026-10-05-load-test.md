# Load test: `/live` spectators and live agents (Workstream D)

5 October 2026, on `feat/full-scope` plus this workstream's branch (sim_0.31.0). Tool:
`tools/ops/load.ts`. Raw results, without per-call latency samples:
`docs/evidence/2026-10-05-load-test.json`.

## Summary

| | Breaking point before the fixes | After the fixes |
|---|---|---|
| Spectators only | **~200**: each checkpoint held the event loop 1.5–1.9 s, a new viewer waited 24 s for its first scene, and RSS reached 1.3 GB at 500 | No break up to the tested ceiling of **1000**: event-loop p99 46 ms, max 258 ms, RSS 538 MB |
| Agents (plus 20 probe spectators) | **~100**: live tick lag over 1.1 s. At 250, up to 84 queries waited for the pool; at 500, observe p99 was 3.1 s | No break up to **500** (354 possessing, 146 queued by the species caps): event-loop p99 62 ms, observe p99 67 ms |
| Mixed | **500 spectators + 250 agents crashed the server** (JavaScript heap out of memory; 500 sockets dropped; health failed) | **1000 spectators + 500 agents** held: event-loop p99 103 ms, live message p95 100 ms, no errors. The main thread was at 84–93% of one core, so this is close to the ceiling on this hardware |

The general `/live` cap defaults to 1000 connections in total (`VANA_LIVE_MAX_CONNECTIONS`).
That is the highest load tested, where the server still met every criterion below, but with
little single-core headroom left. Raise it only after a run on the real host.

## Hardware and setup

- **Host:** Apple M4, 10 cores, 16 GB, macOS 26.6.
- **Docker:** a Colima VM with 4 CPUs and 8 GB, running Ubuntu 24.04 and Docker 29.5. The VM
  also ran the owner's staging world and the E2E stack.
- **Stack under test:** a private instance of the E2E setup, `COMPOSE_PROJECT_NAME=vana-load`
  (`deploy/compose.yml` + `tools/e2e/compose.e2e.yml`), on a fresh island world (seed 1,
  about 1,820 animals, 12 world hours per real hour, rewards and live agents on). Limits:
  - server: 3 CPUs, 2 GB;
  - PostgreSQL: 1 CPU, 1 GB;
  - Caddy: 2 CPUs, 512 MB;
  - load generator: 1 CPU, 1 GB.
- **Load generator:** `tools/ops/load.ts`, bundled with esbuild and run as a `node:22-alpine`
  container in the Caddy container's network namespace. Traffic goes through Caddy
  (`http://localhost`) exactly as a visitor's would. Metrics are read straight from
  `server:9464` (`VANA_METRICS_HOST=0.0.0.0` in this private stack only). Server CPU and RSS
  come from its own `process_*` metrics: CPU % is per core, so 100 = one core. The
  generator never used more than 18% of its one CPU, so it was not the bottleneck.
- **Spectators:** each opens `/live`, sends a `view` every second (a camera near a random
  animal, radius 300–1500 m) and switches to following a random animal about every 30 s. That
  is busier than a real viewer. Spectator steps measure 330 s, so each catches a checkpoint
  broadcast (one every 5 real minutes at 12×).
- **Agents:** each is a separate instance of the published `client.mjs` with its own HOME
  and profile. They were registered beforehand, paced by the per-network registration bucket,
  which took about 55 minutes for 500. Each agent observes every 2 s, possesses a herbivore
  (spread over species), and moves about 40 m every 3–5 s. Twenty probe spectators watch the
  whole island, so they receive every agent at 4 Hz. Agent steps measure 150 s.
- **"Broken"** means any of these over the window:
  - event-loop p99 above 250 ms, or live tick lag above 500 ms;
  - agent call p99 above 1 s;
  - live message p95 above 1 s;
  - any 5xx, failed health check or dropped connection;
  - the world clock falling behind.

### Why the generator runs inside the VM

The first runs drove the stack from macOS through Colima's forwarded ports (28080, then
28095). At about 500–1000 host-forwarded WebSockets, **Colima's port forwarding and its
Docker socket stopped working, twice**: every connection dropped with 1006, and the
socket was unreachable until Colima was restarted. That is a limit of this local
development setup, not a server result, and it affected other sessions sharing the VM. All
results below come from the in-VM generator. Never run load tests through a desktop VM's
port forwarding.

Notes on these results:

- **Errors.** No step had a 5xx, a dropped socket, a slow-consumer cut-off, a failed health
  check, a waiting pool query or any world-clock lag. The only refusals were a handful of
  `409 not_on_land` moves: random points that fell in water, a correct answer.
- **Why 354 of 500 agents possess.** At most a fifth of each species can be steered by
  agents, so on this island no more than 354 animals can be possessed at once. The other 146
  agents wait in the species queues, as designed, and keep observing. Slots
  (`VANA_AGENT_SLOTS`) are therefore not the limit for playing agents on this island; the
  possession caps are.
- **The one high value.** The 1026 ms live-message p99 at 500 + 250 is a single checkpoint
  moment, when 500 scenes were being deflated. The 1000 + 500 run, with twice as many
  viewers, stayed at a 126 ms p99.

## Bottlenecks found and fixed

Each fix was profiled first with the V8 CPU profiler, attached inside the container through
the inspector. Each has a regression test.

1. **Every viewer got its own copy of the scene.** At each checkpoint the gateway built a
   ~1.6 MB string for every viewer, and `ws` turned each one into a new Buffer. Deflate also
   ran at level 6.
   - Measured at 500 spectators: event loop max 1.94 s, scene broadcast 1.86 s, RSS 1.3 GB, new
     viewers' first-scene p95 3.5 s. On the shared E2E stack, 200 spectators already gave a
     1.7 s loop and a 24 s first scene.
   - Fix: viewers due the same message share one encoded Buffer, still sent as a text frame;
     deflate runs at level 3 (10.7 ms instead of 24 ms per scene, 10% more bytes).
   - Result at 500 spectators: loop max 0.23 s, broadcast 62 ms, RSS 376 MB, first-scene p95
     102 ms.
   - Commit: `perf(gateway): share one encoded scene per message…`. Test: `gateway.test.ts` ›
     sends immutable route geometry once per checkpoint (asserts the shared Buffer) and the
     real-socket cap test (asserts text frames).
2. **Every signed agent call wrote `last_seen_at`.**
   - Measured at 250 agents: about 600 updates a second, up to 84 queries waiting for the
     10-connection pool; at 500, 98 waiting and observe p99 3.1 s.
   - Fix: write it at most once a minute per agent from this process. It is only used to reap
     agents unseen for 14 days.
   - Result: the pool never waited again.
   - Commit: `perf(live): write an agent's last-seen time at most once a minute`. Test:
     `agentTouch.test.ts`.
3. **The 4 Hz live broadcast serialized the visible agents once for every viewer.** This
   crashed 500 spectators + 250 agents: the heap ran out of memory and the server restarted.
   - Fix: each agent, wild chaser and the drop list are serialized once per broadcast and
     joined per viewer.
   - Result: 1000 + 500 runs with a live broadcast max of 96 ms.
   - Commit: `perf(gateway): serialize each live agent once per broadcast`. Test:
     `gateway.test.ts` › serializes each agent once per live broadcast, not once per viewer.
4. **`nearby()` sorted by two `Math.hypot` calls per comparison.** It runs for every agent every
   second (the wild-hunter scan, 1200 m, nearest 60) and for every observe (900 m, nearest 120).
   - Measured: 46% of all server CPU at 500 agents, a 1.7 s event-loop max, observe p99 6.5 s.
   - Fix: squared distances, computed once.
   - Result: 13% of CPU. At 20 + 500: loop p99 62 ms, observe p99 67 ms.
   - Commit: `perf(live): sort nearby animals by a precomputed squared distance`. Test:
     `liveLayer.test.ts` › indexed lookups (now also checks the wide, cut-to-60 shape against a
     full scan).

## What is left, in order of cost at the top step

From the last profile, at 500 agents:

- the observe handler's other work (about 24% inclusive): building each agent's nearby list,
  water and drops;
- the wild-hunter scan;
- request signature checks (Ed25519 verify, about 4%);
- HTTP writes.

All of it runs on the one main thread. With 1000 spectators and 500 agents the server
used 84–93% of one core while three were allowed, so the next limit on this hardware is
single-core CPU, at about 1000–1200 viewers with 500 agents. Beyond that, these would help:

- move per-viewer deflate of checkpoint scenes off the critical path, for example with
  pre-compressed frames;
- cache an agent's nearby list for its 2 s observe interval;
- run the agent API in a worker thread.

## How to run it

```bash
# A private stack (never the staging or shared E2E projects), with resource limits in an override.
COMPOSE_PROJECT_NAME=vana-load VANA_E2E_ENV=/private/path/load.env VANA_E2E_PORT=28095 tools/e2e/stack.sh up
# Register agents once (paced by the per-network registration bucket: ~55 min for 500).
npx tsx tools/ops/load.ts --base http://localhost:28095 --register 500 --profiles .ci-artifacts/load/agents
# Profiles are bound to the URL they were made for; for the in-VM run below, rewrite "base" in
# each .ci-artifacts/load/agents/*/.vana-agent/load.json to http://localhost/api.
# Bundle and run the generator inside the VM, in the Caddy container's network namespace.
npx esbuild tools/ops/load.ts --bundle --platform=node --format=esm --target=node22 \
  --external:bufferutil --external:utf-8-validate \
  "--banner:js=import { createRequire } from 'node:module'; const require = createRequire(import.meta.url);" \
  --outfile=.ci-artifacts/load/load.mjs
docker run --rm --network container:vana-load-web-1 --memory 1g --cpus 1 -v "$PWD:$PWD" -w "$PWD" node:22-alpine \
  node .ci-artifacts/load/load.mjs --base http://localhost --metrics-url http://server:9464/metrics --stats metrics \
  --profiles "$PWD/.ci-artifacts/load/agents" --steps 50:0,200:0,500:0,1000:0 --duration 330 --out "$PWD/.ci-artifacts/load/spectators.json"
```

The metrics URL needs `VANA_METRICS_HOST=0.0.0.0` on that private stack's server, set in the
same override as the limits.
